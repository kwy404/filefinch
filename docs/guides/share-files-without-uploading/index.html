Start sendingHow it works

Most ways of sharing a file start with an upload. You push the file to someone else's server, wait, copy a link, and the other person downloads it again. That works, but it means two full trips over the internet and a copy of your file sitting on a computer you do not control, often for days.

There is another way to share files without uploading them anywhere first. Two browsers can open a direct connection and pass the file from one device to the other while both are online. filefinch is a free, open source web app built around exactly that idea. This guide explains how it works, how to do it step by step, and when an upload is honestly the better choice.

What "without uploading" really means

When people say they want to share a file without uploading it, they usually mean one or more of these things:

  • No copy of the file should be stored on a third party server.
  • No account, sign up or email address should be needed.
  • The file should arrive exactly as it was sent, not shrunk or converted.
  • The receiver should not have to wait for an upload to finish before the download can start.

A direct, peer to peer transfer covers all four. The sender's browser reads the file in small chunks and hands each chunk straight to the receiver's browser over a WebRTC data channel. Nothing is parked in the middle waiting to be picked up. When the transfer ends, the only copies are the one you started with and the one the receiver saved.

How filefinch connects two devices with no server

Most direct transfer tools still rely on a signaling server, a small service that introduces the two devices to each other. filefinch skips that too. The site is static, hosted on GitHub Pages, and no backend of ours takes part in the connection.

Instead, the introduction happens through a link or a QR code:

  1. The first device creates an invite. The browser gathers the network details it needs, compresses them and packs them into a link and a QR code.
  2. The second device opens that link or scans the QR code. It produces a short reply code, also shown as a link or QR code.
  3. The reply goes back to the first device, either through any messenger you like or by showing the QR code to the first device's camera.

That single round trip is enough. From then on the two browsers talk directly. If camera scanning is not available in your browser, you can always paste the codes by hand.

The invite contains the network addresses of the device that made it. Share it only with your own device or the person you are sending to, and use each invite for one connection.

Step by step: share a file without uploading

  1. Open filefinch on the device that has the file. There is nothing to install, though you can add it to your home screen if you like.
  2. Create an invite and send the link to the other device, or let the other device scan the QR code.
  3. On the receiving device, open the link. A reply code appears.
  4. Send the reply back, or point the first device's camera at the reply QR code.
  5. Check that both screens show the same short connection fingerprint, then pick your files and send.

Both devices can send in either direction over the same connection, so once you are connected, the receiver can send files back without creating a new invite.

Why skipping the upload helps

Privacy

Your file never becomes an object on someone else's storage. There is no account to tie it to, and filefinch has no analytics or tracking. WebRTC always encrypts the connection with DTLS, using keys that the two browsers generate for that one session. If you want an extra layer, both people can type the same passphrase, and every chunk is sealed again with AES-GCM before it leaves the sender. The passphrase itself is never sent.

Speed

With an upload, the file crosses the internet twice: up to the server and down again. A direct transfer crosses once, and the receiver gets data while you are still sending. On the same Wi-Fi or wired network the traffic usually stays inside your home or office, which is often much faster than uploading. Across the internet, speed is limited by the slower of the two connections, which is typically the sender's upload speed.

Integrity

Files are sent byte for byte. Photos and videos keep their original quality and their metadata. Each file is hashed with SHA-256 as it streams, and the receiver checks that hash at the end, so you know the copy matches the original.

No size cap from us

filefinch does not set a file size limit. The practical limits are free disk space on the receiver, both devices staying online, and the way the browser saves files. If the connection drops, you reconnect and the transfer continues from the last confirmed point instead of starting over. The guide to sending large files without limits covers this in more detail.

Sharing folders, not just files

You can send a whole folder, and filefinch rebuilds the tree on the other side. Paths coming from the other device are treated as untrusted and cleaned up, so nothing can be written outside the folder you choose, and name clashes get a unique name. If you share the same folder regularly between two of your own machines, folder sync can send only what changed, after you approve a plan of the changes. The whole folder guide explains both options.

When filefinch is not the right tool

Being direct has a cost: there is no mailbox in the middle. Both devices must be online at the same time with filefinch open. If the person you are sending to is asleep, traveling or simply not around, a cloud upload or an email attachment is the better tool, because the file can wait for them.

A few other honest limits:

  • On phones, mobile browsers may pause a tab in the background. Keep the screen on during long transfers.
  • Some networks block direct connections, for example strict corporate firewalls or carrier grade NAT on some mobile networks. In that case a TURN relay is needed. filefinch explains when this happens and lets you add your own TURN servers in Settings. A relay forwards only encrypted packets, but it can see both IP addresses and how much data flows.
  • If you need a link that many people can open over several days, that is a publishing job, and a hosting or cloud service fits it better.

A quick checklist before you send

  • Both devices have filefinch open and are online.
  • The receiver has enough free disk space for everything you are sending.
  • You shared the invite only with the intended device or person.
  • Both screens show the same connection fingerprint.
  • For long transfers on a phone, the screen stays on.

When all five are true, open the app and send. For a closer look at how the connection itself works, read peer to peer file transfer explained, or see the privacy section on the home page.

Questions people ask

Can I share a file without uploading it to the cloud?

Yes. With a direct browser to browser transfer, the file goes from your device to the receiver's device over an encrypted WebRTC connection. filefinch does this for free with no account, and no copy is stored on a server.

Do both people need to be online at the same time?

Yes. There is no mailbox in the middle, so both devices must be online with filefinch open while the transfer runs. If the receiver cannot be online, a cloud upload or an email attachment is the better choice.

Is there a file size limit when sharing without uploading?

filefinch does not set one. The practical limits are free disk space on the receiver, both devices staying connected and the way the browser saves files. Interrupted transfers can resume from the last confirmed point.

Does the receiver need to install an app?

No. Any modern browser such as Chrome, Edge, Firefox or Safari works, on phones, tablets and computers. You can optionally install filefinch from the browser so it opens like an app.

Can anyone else see the files I share this way?

The connection is encrypted with DTLS, with keys generated by the two browsers. If a TURN relay is needed, it forwards only encrypted packets, though it can see the IP addresses and the amount of data. You can add a passphrase for a second layer of encryption.
